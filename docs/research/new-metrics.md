# Переработанные метрики для валидации гипотез

## Сводная карта гипотез и способов проверки

| Гипотеза | Утверждение (короткое) | Способ проверки |
|---|---|---|
| H1 | Inline-цитаты → время верификации ↓30% | **Опрос пользователей** (структура метрик не прорабатывается) |
| H2 | Семантическое расширение → recall@10 ↑15% | **Бенчмарк-сравнение** 3 представителей × 100 кейсов |
| H3 | Итеративный feedback → precision@10 ↑10% за 3 итерации | **Прогон WideResearcher в 3 итерации** на тех же 100 кейсах |
| H4 | Посегментная привязка цитат → доверие +1.0 (Лайкерт) | **Опрос пользователей** (структура метрик не прорабатывается) |
| H5 | Feedback-aware версионирование → качество +1.0 | **Опрос пользователей** (структура метрик не прорабатывается) |
| H6 | Планировщик → freshness-coverage ↑30% | **Качественная фиксация** (без количественного бенчмарка) |

## Часть 1. Бенчмарк для H2 и H3

### 1.1. Дизайн бенчмарка

**Кейсы:** 100 промптов глубокого исследования = **20 категорий × 5 кейсов в каждой**. Описание и список — в [`cases.md`](cases.md). Машинно-читаемый вход для скрипта — `data/input-cases.json`.

**Категории** (от природы к науке, через социум, экономику и культуру — даёт срез по разной плотности источников, свежести и спорности):

| Группа | Категории |
|---|---|
| Естественные науки | Биология и экология · Физика и космос · Химия и материалы · Науки о Земле |
| Технологии | AI / ML · Software Engineering · Кибербезопасность · Hardware и инфраструктура |
| Медицина | Клиническая медицина · Фармакология · Психология и нейронауки |
| Гуманитарные | История · Лингвистика и литература · Философия и этика · Право и политология |
| Экономика | Экономика и рынки · Бизнес и менеджмент · Криптовалюты и блокчейн |
| Культура | Искусство и кино · Спорт |

В каждом кейсе фиксируется уровень `freshness` (low / mid / high) — это даёт срез метрик не только по категориям, но и по зависимости от свежести источников (косвенно подкрепляет H6).

**Представители (3 системы):**

| № | Система | Модель |
|---|---|---|
| A | Самая слабая коммерческая OpenAI Deep Research | (модель провайдера) |
| B | **WideResearcher** | Qwen 3.5 9B (local) |
| C | Популярный OSS Deep Researcher | Qwen 3.5 9B (local) |

> Логика контрольных сравнений: A vs B — «как мы относительно коммерческого baseline»; **B vs C — главный контроль для H2/H3** (одна и та же модель, разные алгоритмы → эффект архитектуры).

### 1.2. Сырые данные, собираемые на кейс

Для каждой пары (кейс, представитель):

| Поле | Тип | Источник |
|---|---|---|
| `answer_text` | str | Финальный ответ системы |
| `sources[]` | list[url] | Все ссылки, на которые ссылается ответ |
| `gen_time_sec` | float | От отправки запроса до получения финального ответа |
| `cost_usd` | float | Стоимость прогона (для локального Qwen = 0) |
| `judge_verdict[i]` | Yes / No | Вердикт LLM-судьи по каждой ссылке: подтверждает ли источник свой тезис |

### 1.3. Производные метрики на кейс

| Метрика | Формула | Смысл |
|---|---|---|
| `n_sources` | `len(sources)` | Объём найденного |
| `n_valid` | `sum(judge_verdict == Yes)` | **Прокси для recall** — сколько подтверждённых источников |
| `validity_rate` | `n_valid / n_sources` | **Прокси для precision** — доля подтверждённых среди найденных |
| `unique_domains` | `len(set(domain(s)))` | Разнообразие источников |
| `time_per_valid` | `gen_time_sec / n_valid` | Эффективность по времени |
| `cost_per_valid` | `cost_usd / n_valid` | Эффективность по стоимости |

### 1.4. Агрегаты — на категорию и в среднем

Для каждой системы считаем по каждой из 20 категорий, по уровням `freshness` и общим итогом:

- `avg_n_valid` ± std → главный показатель для **H2** (объём подтверждённых источников)
- `avg_validity_rate` ± std → базовый уровень precision (для **H3** будет сравниваться с итерацией 3)
- `avg_unique_domains` ± std → диверсификация
- `avg_gen_time` ± std → производительность
- `avg_cost` ± std → стоимость
- `avg_time_per_valid`, `avg_cost_per_valid` → нормированная эффективность

### 1.5. Таблица итоговых результатов (макет)

| Метрика | OpenAI DR | OSS DR (Qwen) | **WideResearcher (Qwen)** |
|---|:---:|:---:|:---:|
| avg_n_valid | … | … | … |
| avg_validity_rate | … | … | … |
| avg_unique_domains | … | … | … |
| avg_gen_time, с | … | … | … |
| avg_cost, $ | … | 0 | 0 |

Плюс — разбивка той же таблицы по 20 категориям и по уровням `freshness` (раздел приложения ВКР).

### 1.6. Критерии приёмки

**H2 (recall ↑15%):** подтверждена, если
```
avg_n_valid(WideResearcher, Qwen) ≥ 1.15 × avg_n_valid(OSS DR, Qwen)
```
Контроль модели — Qwen 3.5 9B в обеих системах → различие отражает алгоритм семантического расширения, а не модель.

**H3 (precision ↑10% за 3 итерации):** см. отдельный прогон в разделе 2.

### 1.7. Структура output одного кейса

Прогон выполняется скриптом [`scripts/run_benchmark.py`](scripts/run_benchmark.py) **по одной системе за запуск** (флаг `--system openai_dr | wide_researcher | oss_dr`, по умолчанию `openai_dr`). Каждая система пишет в свой файл — `data/results-{system}.jsonl` — **итеративно** (одна JSONL-строка на завершённый кейс). После прогонов всех трёх систем файлы объединяются по `case_id` для агрегации в раздел 1.5.

Секреты систем (`OPENAI_API_KEY`, `WIDE_RESEARCHER_URL`/`TOKEN`, `OSS_DR_URL`/`TOKEN`, тарифы стоимости) вынесены в `.env` — см. `.env.template`.

```json
{
  "case_id": "BIO-01",
  "category_code": "BIO",
  "category": "Биология и экология",
  "prompt": "Эпигенетическое наследование стресса...",
  "freshness": "mid",
  "started_at": "2026-05-16T10:00:00+00:00",
  "finished_at": "2026-05-16T10:05:30+00:00",
  "systems": {
    "openai_dr": {
      "status": "ok",
      "error": null,
      "answer_text": "...",
      "sources": ["https://...", "https://..."],
      "gen_time_sec": 45.2,
      "cost_usd": 0.50,
      "judge_verdicts": [
        {"url": "https://...", "verdict": "Yes", "reasoning": "..."},
        {"url": "https://...", "verdict": "No",  "reasoning": "..."}
      ],
      "metrics": {
        "n_sources": 5,
        "n_valid": 4,
        "validity_rate": 0.8,
        "unique_domains": 4,
        "time_per_valid": 11.3,
        "cost_per_valid": 0.125
      }
    },
  }
}
```

В одном прогоне `systems` всегда содержит **один ключ** — выбранную через `--system` систему. После трёх прогонов получится три файла, объединяемые по `case_id`.

**Поля верхнего уровня:**

| Поле | Тип | Описание |
|---|---|---|
| `case_id` | str | Совпадает с `id` из входного файла |
| `category_code`, `category`, `prompt`, `freshness` | … | Скопированы из входного кейса (избыточно, но удобно для агрегации без join) |
| `started_at`, `finished_at` | ISO-8601 UTC | Временные границы прогона |
| `systems` | obj | Один ключ — выбранная система (`openai_dr` / `wide_researcher` / `oss_dr`) |

**Поля внутри одной системы:**

| Поле | Тип | Описание |
|---|---|---|
| `status` | `"ok"` / `"error"` | Если `"error"` — содержательные поля заполнены пусто/нулями |
| `error` | str / null | Тип и сообщение ошибки при `status="error"` |
| `answer_text` | str | Финальный ответ системы |
| `sources` | list[url] | Все ссылки-источники в ответе |
| `gen_time_sec` | float | От старта запроса до получения финального ответа |
| `cost_usd` | float | Денежная стоимость прогона (0 для локальных Qwen-систем) |
| `judge_verdicts[]` | list[obj] | Один объект на каждую ссылку: `{url, verdict: "Yes"/"No", reasoning}` |
| `metrics` | obj | Производные метрики из раздела 1.3 |

**Гарантии скрипта:**

- Каждая строка JSONL — независимый, валидный JSON.
- Запись с `flush + fsync` — устойчиво к падению.
- При повторном запуске уже завершённые `case_id` пропускаются (можно отключить флагом `--no-resume`).
- Срез по входу: `--slice 0:5`, `--slice 10:`, `--slice 5`.

## Часть 2. Отдельный прогон для H3 (итеративный feedback)

### 2.1. Дизайн

Те же 100 кейсов прогоняются **только через WideResearcher** в режиме 3 итераций с feedback:

- **Итерация 1** — базовый ответ. LLM-судья (он же симулятор пользователя) расставляет сегментам метки like / dislike по тому же критерию, что и судья ссылок.
- **Итерация 2** — пайплайн корректирует пул запросов через метки → новый ответ.
- **Итерация 3** — финальный ответ.

### 2.2. Метрики на итерацию

| Метрика | Считается на каждой итерации |
|---|---|
| `validity_rate@iter` | n_valid / n_sources после итерации k |
| `n_valid@iter` | абсолют |
| `Δvalidity_rate` | validity_rate@3 − validity_rate@1 |

### 2.3. Критерий приёмки H3

```
avg_validity_rate@iter=3  ≥  avg_validity_rate@iter=1 × 1.10
```

Считается по всем 100 кейсам и отдельно по каждой из 20 категорий.

## Часть 3. Судья (LLM-as-a-Judge)

Единая модель-судья для обеих частей. Вердикт по ссылке — `Yes` / `No`:

- **Yes** — источник реально подтверждает тезис, к которому привязана цитата.
- **No** — источник не подтверждает / отсутствует / содержит противоположное.

Промпт судьи и его модель фиксируются **до прогона**. Для прозрачности — выгружается набор `(тезис, ссылка, вердикт)` под OSI-лицензией вместе с бенчмарком.

## Часть 4. H6 — текстовая фиксация (без количественного бенчмарка)

### 4.1. Темы (предложение, 5 шт.)

Темы с заведомо высокой частотой обновления:

1. Курсы и рынки криптовалют.
2. Релизы и обновления AI-моделей / фреймворков.
3. Политические новости (любой регион).
4. Спортивные результаты текущего сезона.
5. Свежие научные публикации (например, последние arXiv по выбранной нише).

### 4.2. Что фиксируем

- Запуск скрипта ежедневно в течение N дней (например, 14).
- Для каждого прогона — список найденных источников и их даты публикации.
- Фиксация в текстовом виде: «дата публикации источников становится свежее с каждым днём» — да / нет.

### 4.3. Подтверждение гипотезы

H6 считается подтверждённой **текстово**, если по большинству тем дата публикации найденных источников сдвигается к более свежей с каждым прогоном. Без количественного порога, без формальной таблицы результатов в ВКР — только описание наблюдения.

## Часть 5. Отличия от старой системы метрик

| Старое (слайд 13) | Новое |
|---|---|
| `recall@10` против BM25 (требует golden set) | `avg_n_valid` против контрольной OSS DR на той же модели |
| `precision@10` после 3 итераций | `avg_validity_rate@iter=3` vs `@iter=1` на тех же 100 кейсах |
| Citation accuracy / Hallucination rate | Объединены в `validity_rate` (вердикт судьи по каждой ссылке) |
| Trust score Лайкерт 4.6 → 6.2 | Вынесено в опрос (H1, H4, H5) |
| 100 кейсов (50 golden + 20 adv + 15 reg + сценарные) | 100 кейсов = 20 категорий × 5, с тегом `freshness` |
| Сравнение только с BM25 baseline | Тройное сравнение: коммерческий + OSS DR + WideResearcher |
